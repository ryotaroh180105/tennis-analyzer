# 08. 導入・保守・運用設計

前提：初期は開発者1名〜数名。**運用の複雑さは負債**として扱い、
「規模が出てから足す」を原則にする（yagni）。ただし
**計測（コスト・精度・失敗率）だけは初日から入れる** — 後から遡れないため。

## デプロイ構成

### 初期（Phase 0〜1、〜数百ユーザー）

| 層 | 構成 | 月額目安 |
|---|---|---|
| API + フロント | VPS 1台（Docker Compose: FastAPI / Next.js / Redis / PostgreSQL） | 2〜5千円 |
| GPUワーカー | サーバーレスGPU（RunPod / Modal 等、ジョブ単位課金）。常駐させない | 従量（下記コストモデル） |
| ストレージ | Cloudflare R2（egress無料が動画配信で効く） | 従量 |
| CDN / DNS / TLS | Cloudflare（無料枠） | 0円 |

- **GPU常駐はしない**。解析はバッチ処理でリアルタイム性不要（目標：実時間の0.5倍）。
  ジョブ投入時にコンテナ起動 → 完了で破棄。コールドスタート1〜2分は許容範囲。
- Kubernetes・マルチリージョン・マイクロサービス分割は**採用しない**（この規模では負債）。
  ワーカーイメージがコンテナ化されていれば、スケール手段は後から差し替えられる。

### スケール時の変更点（それまでやらない）

- API層をマネージドに移す（Cloud Run 等）、DBをマネージドPostgreSQLに
- GPUワーカーのキュー並列度を上げる（Celeryのconcurrency設定のみ、設計変更なし）

## 環境とリリース

- 環境は **dev（ローカル）と prod の2つ**。stagingは作らない。
  代わりに prod で**ゴールデンセット回帰**（下記）を通してからリリース。
- リリース単位は3種類あり、それぞれ独立にバージョン管理・ロールバックする：

| 種類 | 対象 | ロールバック手段 |
|---|---|---|
| アプリコード | API / フロント / ワーカー | コンテナイメージのタグ切り戻し |
| CVモデル | 検出・追跡・分類モデルの重み | モデルレジストリのバージョン指定（S3にバージョン付き保存） |
| 設定YAML | taxonomy / advice-rules | バージョン付きファイル追加方式（既存を書き換えない、[04](04-miss-taxonomy.md)） |

- EventStream・MatchFeedbackがバージョン付き（[02](02-architecture.md)）なので、
  モデル・YAML更新時は**過去結果を上書きせず再計算結果を並存**できる。
  ユーザー向けには最新版のみ表示。

## ゴールデンセット回帰（品質ゲート）

- 撮影条件の異なる実動画 **10〜20本**（オムニ/ハード、晴/曇、画角良/悪）を正解ラベル付きで固定保持。
- モデル・パイプライン・YAML変更時に全ステージを再実行し、ステージ別の精度指標を前版と比較。
  劣化があればリリースしない。
- ユーザー修正データ（`user_corrections`）は毎月ゴールデンセットに還流し、
  「実ユーザーの失敗ケース」を増やす。**これが精度改善の主ループ**。

## 監視・アラート（初日から入れるもの）

| 対象 | 指標 | 手段 |
|---|---|---|
| 解析ジョブ | 失敗率、所要時間/動画実時間比、キュー滞留数 | ジョブテーブル + 簡易ダッシュボード（Grafana 1枚） |
| エラー | 例外の集約 | Sentry（無料枠） |
| コスト | 動画1本あたりGPU秒・Claudeトークン・ストレージ増分 | ジョブ完了時にレコード化（**1本単位で原価が見える状態を最初から作る**） |
| 精度 | unknown率、ユーザー修正率（=不満の先行指標） | 週次で集計、しきい値超過をアラート |
| 死活 | API応答、LINE Webhook | UptimeRobot（無料枠） |

- ユーザー修正率は**プロダクト指標であると同時に運用アラート**。
  急上昇＝新しい撮影環境・コート種別への未対応を意味することが多い。

## コストモデル（1試合＝1時間動画あたりの変動費・概算）

| 項目 | 概算 | 前提 |
|---|---|---|
| GPU解析 | 15〜40円 | 実時間0.5倍 × サーバーレスGPU（L4/T4級 $0.5〜1.0/h） |
| エンコード（CPU） | 〜5円 | `-c copy` 優先でエンコード最小化（[02](02-architecture.md)） |
| ストレージ | 月10〜20円/本 | 原本4〜6GB + 成果物、R2 $0.015/GB/月。保持ポリシーで抑制（下記） |
| Claude API | 10〜30円 | スタッツJSON数千トークン + 出力数千トークン、Opus 4.8。ドメインプロンプトはキャッシュ済み |
| 配信 | ほぼ0円 | R2 egress無料 |
| **合計** | **50〜100円/試合** | 価格設計の下限制約（[09](09-go-to-market.md)） |

- 数値は設計時の概算。**実測値でこの表を更新することが運用タスク**
  （上記「1本単位の原価レコード」がそのまま使える）。

## データライフサイクル・プライバシー

| データ | 保持 | 理由 |
|---|---|---|
| 原本動画 | 無料ユーザー30日 / 有料ユーザー1年（設定で延長可） | ストレージが原価の主変動要因。編集済み動画とイベントJSONが残れば振り返り価値は保てる |
| 編集済み・ハイライト | プラン継続中は保持 | プロダクトの本体 |
| イベントJSON・スタッツ | 無期限 | 軽量。傾向分析・アドバイスの原資 |
| ユーザー修正ラベル | 無期限（匿名化して学習利用） | 精度改善の主ループ。利用規約に学習利用を明記し、オプトアウト可能に |

- 削除ポリシーは**期限前にLINEで通知**（「原本の保存期限が近い」）。有料化の自然な動機にもなる。
- 相手プレーヤーの映り込み：共有リンクは既定で相手の個人スタッツを含めない（[07](07-advice-delivery.md)）。
  アカウント削除時は動画・スタッツを含め全消去（学習利用済みの匿名化データを除く）。
- 未成年（部活層）：保護者同意のフローは**スクール・チーム経由の導入時にまとめて取得**する設計とし、
  個人向けには年齢確認のみ（[09](09-go-to-market.md) のセグメント参照）。

## サポート運用

- 問い合わせ窓口は**LINE公式アカウントに一本化**（配信チャネルと同一。メールは補助）。
- 「解析がおかしい」報告は専用フローにする：該当試合IDと区間を選ばせる → 
  `user_corrections` と同じ形式で記録 → ゴールデンセット候補に自動追加。
  **サポートコストを学習データ収集に転換する**のがこのプロダクトの構造的な強み。
- FAQ・撮影ガイドはアプリ内に置き、LINEのリッチメニューからリンク。

## 障害時の縮退運転

パイプラインはステージ独立（設計原則3）なので、部分障害は部分縮退で受ける：

| 障害 | 縮退 |
|---|---|
| GPUワーカー不調 | ジョブをキューに滞留させ「混雑中、完了時にLINE通知」。データは失わない |
| Claude API障害 | 編集動画・スタッツまで配信し、フィードバック文は後追い生成（ジョブ再実行） |
| LINE API障害 | アプリ内通知にフォールバック |
| ストレージ障害 | アップロード受付を停止（明示メッセージ）。既存動画の閲覧はCDNキャッシュで一部継続 |

- 非リアルタイム・バッチ型のプロダクトなので、**「遅れます」が言えれば大半の障害は致命傷にならない**。
  ジョブの冪等性（同一入力での再実行安全）だけは実装時に保証すること。
