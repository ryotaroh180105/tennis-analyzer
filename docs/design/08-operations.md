# 08. 導入・保守・運用設計

前提：初期は開発者1名〜数名。**運用の複雑さは負債**として扱い、
「規模が出てから足す」を原則にする（yagni）。ただし
**計測（コスト・精度・失敗率）だけは初日から入れる** — 後から遡れないため。

## デプロイ構成

### 初期（Phase 0〜1、〜数百ユーザー）

| 層 | 構成 | 月額目安 |
|---|---|---|
| API + フロント | VPS 1台（Docker Compose: FastAPI / Next.js / Redis / PostgreSQL） | 3〜5千円 |
| GPUワーカー | サーバーレスGPU（RunPod / Modal 等、ジョブ単位課金）。常駐させない。ingest正規化（NVENC）もここで実行 | 従量（下記コストモデル） |
| ストレージ | Cloudflare R2（egress無料が動画配信で効く）。低頻度アクセス層へのライフサイクル移行を併用 | 従量 |
| CDN / DNS / TLS | Cloudflare（無料枠） | 0円 |
| LINE公式アカウント | ライトプラン（月5,000通） | 5千円 |

- **GPU常駐はしない**。解析はバッチ処理でリアルタイム性不要。
  ジョブ投入時にコンテナ起動 → 完了で破棄。コールドスタート1〜2分は許容範囲。
- **ただし並列度は初日からキュー長連動**（min=0, max=キュー長、上限N）にする。
  動画の到着は週末夕方に集中するため、1並列固定では日曜夜に数時間待ちが発生し
  「アップロード完了→納品 実時間1.0倍以内」（[01](01-mvp-scope.md)）が守れない。
- Kubernetes・マルチリージョン・マイクロサービス分割は**採用しない**（この規模では負債）。

### スケール時の変更点と移行トリガー

- API層をマネージドに移す（Cloud Run 等）、DBをマネージドPostgreSQLに。
- **オンデバイス処理への移行トリガー**（世界規模のシェア争いは限界費用が低い側が勝つ。
  サーバーGPU一辺倒はFree層が増えるほど赤字が線形に増える構造のため、転換パスを予め定義する）：
  - 条件：月間GPU変動費がPro売上の30%を超える、または MAU 5,000 超
  - 内容：ステージ独立設計（不変原則3）を活かし、軽量な前処理（活動量ベースの粗カット＝
    ステージ4相当）を端末側に移す。アップロード量が減り、原価とファネル障壁の両方に効く。
    この時点でPWA→ネイティブ（CoreML/NNAPI）を判断する。
  - **制約：端末で削った区間を「破棄」しない**。低活動区間は低ビットレート・低解像度で
    送る（破棄すると、ユーザーが削られた区間を復活修正できなくなり、
    「修正→正解データ→回帰」ループ＝主要moatの入力が構造的に消える）。
  - この判断のため、**GPU秒の内訳（ステージ別）を初日からメトリクスに残す**。

## 環境とリリース

- 環境は **dev（ローカル）と prod の2つ**。stagingは作らない。
  代わりに prod で**ゴールデンセット回帰**（下記）を通してからリリース。
- リリース単位は3種類あり、それぞれ独立にバージョン管理・ロールバックする：

| 種類 | 対象 | ロールバック手段 |
|---|---|---|
| アプリコード | API / フロント / ワーカー | コンテナイメージのタグ切り戻し |
| CVモデル | 検出・追跡・分類モデルの重み | モデルレジストリのバージョン指定（S3にバージョン付き保存） |
| 設定YAML | taxonomy / advice-rules / segmentation / court-spec | バージョン付きファイル追加方式（既存を書き換えない、[04](04-miss-taxonomy.md)） |

- EventStream・MatchFeedbackがバージョン付き（[02](02-architecture.md)）なので、
  モデル・YAML更新時は**過去結果を上書きせず再計算結果を並存**できる。

## ゴールデンセット回帰（品質ゲート）

- 撮影条件の異なる実動画を正解ラベル付きで固定保持。**規模の到達計画**：
  M3開始時に3本（オムニ/ハード/画角悪。調達は[10](10-phase0-implementation-plan.md)のM1タスク）→
  Phase 0 完了までに10本 → Phase 1 公開までに20本（ダブルス・ナイター・雨上がりオムニを含む）。
- モデル・パイプライン・YAML変更時に全ステージを再実行し、ステージ別の精度指標を前版と比較。
  劣化があればリリースしない。合否判定のアルゴリズムと基準
  （**precision ≥ 0.90 かつ recall ≥ 0.80**）は [10](10-phase0-implementation-plan.md) の
  擬似コードが正（この文書では重複定義しない）。
- ユーザー修正データ（segments の user 行、Phase 1以降は PointRecord の修正）は
  毎月ゴールデンセットに還流する。
  **この「修正→正解データ→回帰→改善」のパイプライン自体が主要なmoat**であり、
  コート環境（オムニ/ハード/クレー）×撮影条件のマトリクスを埋めていく世界共通の資産
  （オムニコートは最初のセルに過ぎない。[09](09-go-to-market.md)）。

## 監視・アラート（初日から入れるもの）

| 対象 | 指標 | 手段 |
|---|---|---|
| 解析ジョブ | 失敗率、所要時間/動画実時間比、キュー滞留数 | ジョブテーブル + 簡易ダッシュボード（Grafana 1枚） |
| エラー | 例外の集約 | Sentry（無料枠） |

| チャネル | LINEブロック率、通知到達率 | 週次。ブロック率上昇＝配信という差別化の核の毀損（[07](07-advice-delivery.md)） |
| 死活 | API応答、LINE Webhook | UptimeRobot（無料枠） |

## コストモデル（変動費・概算）

前提を明示する：**為替150円/$**、L4級サーバーレスGPU **$0.5〜1.0/h**、1時間試合。
数値は設計時概算であり、**実測値でこの表を更新することが運用タスク**。

### 1試合あたり処理費

| 項目 | 概算 | 前提 |
|---|---|---|
| precheck（CPU） | 〜数円 | ffprobe＋先頭60秒判定。GPU起動前に入力不正・撮影NGを弾く（[03](03-recording-guidelines.md)） |
| ingest正規化（HEVC→H.264 8Mbps、NVENC） | 15〜45円 | 実時間の0.2〜0.3倍 × $0.5〜1.0/h。**iPhone既定はHEVCでhls.jsが再生できないため必須工程**。実態はI/O支配のためmetricsでDL/エンコード/UL分計（[02](02-architecture.md)） |
| GPU解析（stage1-4） | 25〜75円 | 実時間の0.3〜0.5倍 × $0.5〜1.0/h |
| 編集・HLS（CPU、`-c copy`） | 〜5円 | 正規化済みH.264へのカットは再エンコードなし |
| Claude API（Pro のみ、①即時フィードバック） | 15〜60円 | 入力8K＋出力2〜4K＋**thinkingトークン（出力課金）**、Opus 4.8。**キャッシュ・Batch割引は原価に見込まない**（[05](05-tech-stack.md)） |
| **処理費合計** | **Free（編集のみ）: 45〜125円 / Pro（フル）: 60〜185円** | |

### ユーザー月次原価（定常状態、処理費以外）

| 項目 | 概算 | 前提 |
|---|---|---|
| ストレージ | Free: 〜60円/月、Pro: 150〜250円/月 | **原本（30日）＋正規化H.264（30/90日）＋HLS の3層残高**で計算（HLSだけ数えない）。R2 $0.015/GB/月。Free（月1試合）: 原本5GB＋正規化4GB＋HLS 3ヶ月分 ≒ 15GB。Pro（月3試合）: 原本15GB＋正規化36GB＋HLS累積（90日超は低頻度層へ移行）≒ 70〜110GB |
| LINE配信 | Free/Pro とも月4〜10通 | **ライトプランは超過購入不可（5,000通ハードキャップ）**。約500人到達でスタンダードプラン（月15,000円〜）へ強制移行 — この固定費ジャンプを資金計画に含める（[09](09-go-to-market.md)）。到達を遅らせるため通知のメール比率を上げられる設計にする（channelsアダプタ） |
| 決済手数料 | Pro: 約35円/月 | Stripe等 3.6% × 980円 |

**Pro 1ユーザー月次P&L（3ケース）**：

| ケース | 月間試合数 | 変動費計（処理費＋月次原価） | 粗利（対980円） |
|---|---|---|---|
| ライト | 1 | 約260〜470円 | 約510〜720円 |
| 平均 | 3 | 約380〜840円 | **約140〜600円** |
| フェアユース上限 | 8 | 約680〜1,770円 | **上限側は赤字** — 上限は8試合、超過は200円/試合の従量。**上限張り付きユーザー（発生率5%想定）の赤字は許容コストとして予算化**し、発生率が10%を超えたら価格・上限を改定（[09](09-go-to-market.md)） |

**Freeユーザー原価：月100〜200円（代表値150円で計画。月1試合、編集のみ・LLMなし）**。
Pro粗利×転換率では賄えないため、**Free原価は獲得原価として明示的に予算化**する。
注意：転換しないアクティブFreeは**毎月発生する経常原価**であり「一度きりのCAC」ではない
（24ヶ月で約3,600円/人）。月次のFree原価総額に予算上限を置く。
**バイラルが機能してFreeが急増する成功シナリオでは、この予算が成長のガバナーになる** —
その時の選択肢は「Free枠を絞る（ループを殺す）」ではなく「予算増額＝投資判断のトリガー」
とする（[09](09-go-to-market.md) の資金計画・stage遷移条件と接続）。

- 固定費：VPS 3〜5千円＋LINE 5千円（500人超で2万円）＋その他 ＝ 月約1万〜2.5万円。
- **損益分岐（Free原価込み）**：転換率4%・アクティブ率50%と仮定すると、Pro 1人の背後に
  アクティブFree約12人（原価1,800円/月）。Pro粗利を平均370円とすると**1人あたり純貢献は
  マイナス**になり得る — 成立条件は「転換率5%以上 or Free原価120円以下 or Proアップセル」。
  この3レバーの実測がPhase 1〜2の最重要ミッション（[09](09-go-to-market.md) のKPI）。

## データライフサイクル・プライバシー

| データ | 保持 | 理由 |
|---|---|---|
| 原本動画（カメラオリジナル） | 全プラン30日で削除（正規化H.264を保持源に） | 最大のストレージ要因。再解析は正規化版から可能 |
| 正規化H.264 | Free 30日 / Pro 90日 | 再編集・再解析の源。期限後はHLSのみ残る |
| 編集済みHLS・ハイライト | Free 90日 / Pro プラン継続中（90日超は低頻度層へ移行） | プロダクトの本体。Proの保持容量上限（200GB。平均利用で3〜4年分）を規約に置き、到達時は古い順のアーカイブ削除を選ばせる |
| ※Phase 0 の適用 | 全ユーザーFree扱いで保持ジョブ（日次バッチ）を[10](10-phase0-implementation-plan.md) M5で実装 | プラン概念はPhase 1の課金開始時に導入 |
| イベントJSON・スタッツ | 無期限 | 軽量。傾向分析・アドバイスの原資 |
| ユーザー修正ラベル | 無期限（学習利用。規約明記・オプトアウト可） | 精度改善の主ループ |

- 削除ポリシーは**期限前にLINE/メールで通知**。有料化の自然な動機にもなる。
- **第三者（対戦相手・映り込み）の扱いは規約とガイドだけでは不十分**（法的リスクは
  [09](09-go-to-market.md) のリスク表参照。専門家レビューを実装前の必須タスクとする）。
  設計として先に持つもの：
  - 共有ページは既定で相手の個人スタッツ非表示（[07](07-advice-delivery.md)）
  - 共有ページに**削除請求導線**（ワンクリックで該当動画の公開停止申請）
  - 顔ぼかしオプション（共有用出力のみ。Phase 1で実装判断）
  - 学習利用は本人（アカウント保有者）の映像・修正ラベルに限定し、
    対戦相手側のデータは学習コーパスから除外できるようトラックIDで分離保存
- 「匿名化」を過信しない：動画は顔・体型・コートで再識別可能。学習利用の単位は
  骨格・軌道等の抽象特徴量とし、映像そのものの二次利用はしない。
- 海外展開時はGDPR/CCPA（映り込み第三者、データポータビリティ、保存期間の法定要件）の
  チェックリストを通すこと。国内前提の本節をそのまま輸出しない。

## サポート運用

- 問い合わせ窓口は**LINE公式アカウント＋メール**（チャネル抽象の上に載せる。[07](07-advice-delivery.md)）。
- 「解析がおかしい」報告は専用フローにする：該当試合IDと区間を選ばせる →
  segments の user 修正と同じ形式で記録 → ゴールデンセット候補に自動追加。
  **サポートコストを学習データ収集に転換する**のがこのプロダクトの構造的な強み。
- FAQ・撮影ガイドはアプリ内に置き、LINEのリッチメニューからリンク。

## 障害時の縮退運転

パイプラインはステージ独立（不変原則3）なので、部分障害は部分縮退で受ける：

| 障害 | 縮退 |
|---|---|
| GPUワーカー不調 | ジョブをキューに滞留させ「混雑中、完了時に通知」。データは失わない |
| Claude API障害 | 編集動画・スタッツまで配信し、フィードバック文は後追い生成（ジョブ再実行） |
| LINE API障害 | メール＋アプリ内通知にフォールバック（チャネルアダプタで自動切替） |
| ストレージ障害 | アップロード受付を停止（明示メッセージ）。既存動画の閲覧はCDNキャッシュで一部継続 |

- 非リアルタイム・バッチ型のプロダクトなので、**「遅れます」が言えれば大半の障害は致命傷にならない**。
  ジョブの冪等性・チェックポイント再開の実装要件は [10](10-phase0-implementation-plan.md) に定義。
