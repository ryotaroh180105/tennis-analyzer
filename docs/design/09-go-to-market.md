# 09. マーケティング・差別化・事業設計

前提：[08](08-operations.md) の再計算済みコストモデル（Pro処理費55〜125円/試合＋月次原価）が
価格設計の制約。競合・市場の定量データは調査結果（§競合調査メモ）に基づく。

## カテゴリ定義：「分析アプリ」ではなく「継続AIコーチング」

SwingVisionの土俵（＝試合分析アプリ）で「日本語版・オムニ対応版」として戦う限り、
上限は**地域2位のローカライズ製品**である。本アプリのカテゴリは：

> **記録 × 継続 × 社会性で上達サイクルを回す、テニスの継続AIコーチング**
> （比喩：テニスの Strava。1回の解析精度でなく、続くことに価値の中心を置く）

- 日本ロコ要素（LINE・オムニコート・草トー文化）は**カテゴリではなくGTM戦術**。
  初期市場（日本）で最速でループを回すための手段であり、輸出しない前提で設計する
  （チャネル抽象・i18n・court-spec外出しは [07](07-advice-delivery.md) / [10](10-phase0-implementation-plan.md) / [05](05-tech-stack.md) 参照）。

| 段階 | 市場 | 鍵 |

| 1（〜PMF） | 日本・個人（社会人サークル） | オムニ対応・LINE・編集自動化ループの確立 |

| 並行 | パデル（欧州・中南米）・ピックルボール（北米） | court-spec.yaml＋競技別taxonomyで検討。CVステージの改修範囲を寸法パラメータに限定する規約（[05](05-tech-stack.md)）が展開コストを決める |

## 差別化と moat

### 差別化の核（2つの構造）

1. **誠実さの設計** — 信頼度を隠さない。「誤った断定より未分類」。
   競合の「自動だが間違う」への直接の回答であり、コーチング製品の信頼の核。
2. **継続の設計** — 解析して終わりでなく「振り返る→改善する→また練習する」ループを
   配信で駆動する。**機能としての参入障壁は低い**（競合がLLM層を足すのは数ヶ月仕事）。

### moat の正直な定義 — 「時間限定の先行」＋「規模に依らない非対称資産」

大手（SwingVision/AceSense）は参入した瞬間から桁違いのユーザー基盤で蓄積を始められる。
「先行蓄積が模倣より速い」は小規模側では一般に成立しない。したがって：

- **防御の第一波は「時間限定の先行」**：競合が日本市場のこの体験（LINE配信・オムニ・
  ダブルス・日本語コーチング）に投資する優先度は低く、12〜24ヶ月の窓は現実的。
  この窓の間に下の非対称資産を確保する。
- **規模に依存しない非対称資産**（大手が後から買えないもの）：
  大会主催者・スクール・コーチとの**関係と独占的データ契約**（大会パッケージの
  撮影・解析データの独占利用権）、および日本環境特化の正解データ。

| 資産 | 蓄積構造 | 地理的可搬性 | 規模依存 |
|---|---|---|---|
| 修正ラベル収集パイプライン | 修正→ゴールデンセット→回帰→改善の仕組み（[08](08-operations.md)）。コート環境×撮影条件のマトリクスを埋める | 世界共通（仕組み） | 仕組み自体は模倣可能。埋めたマトリクスが資産 |
| AdviceLog（アドバイス→行動変容→成果） | どの介入がどの層に効いたか（[07](07-advice-delivery.md)）。**中核データはPro母数からしか貯まらない**（Freeの活動サマリ配信から取れるのは開封・リアクションのみ） | 世界共通・競技横断 | **規模依存** — 単独ではmoatにならない |
| 日本環境の正解データ | オムニ・スマホ撮影・ダブルスの学習データ | 日本ローカル | 非対称（大手の優先度が低い） |
| 大会・コーチの関係資産 | 主催者との有償パッケージ＋データ独占契約 | ローカルだが方式は輸出可能 | **非対称**（関係は買収でしか買えない） |
| YAMLルール資産 | コーチ知見のルール化・taxonomyバージョンの蓄積 | 言語キー追加で可搬 | 中立 |

## 獲得：3層のループ設計

### 第1層：クレーム導線（サークル内。K係数の主エンジン）

従来案「共有→視聴→登録」の弱点：共有先は**同じ試合に映っている仲間**であり、
その試合は解析済みなので登録動機が弱い。またサークルの撮影者は1人いれば足りるため、
**登録がサークル単位で1アカウントに収束する**。これを逆手に取る：

```
撮影者がアップロード → サークルLINEに共有
  → 視聴ページに「この試合に映っているのはあなた？ **自分のプレー集を受け取る**」
  → 対戦相手・パートナーが自分をクレーム（撮影者の承認制）
  → 同じ1本の動画から、映っている全員（ダブルスなら4人）がアカウント化
```

- 登録動機を「他人の試合を見る」から「**自分のデータを受け取る**」に変える。
  1動画＝最大4アカウントで、1サークル1撮影者問題がそのまま増幅器になる。
- **クレーム特典は「Phase 2のCVが確実に返せるもの」で約束する**：
  本人が映るポイントのクリップ集＋活動サマリ（プレー時間・ラリー数）。
  個人のミス分類スタッツは**約束しない** — ダブルス遠側は精度が最も出ないケースであり
  （[02](02-architecture.md) ステージ6）、ByteTrackのID switchでトラック紐付け自体が
  誤り得る。個人スタッツは信頼度が立つ範囲（近側・シングルス）から段階提供。
- **「本人確認」の実装定義を正直に置く**：機械的な同一性確認は不可能。実態は
  「LINEログイン＋撮影者の目視承認」であり、これで防げるのは無関係な第三者の
  なりすましまで。撮影者の誤承認・黙認（対戦相手の弱点収集という悪用動機）は
  残るため、(a) クレーム成立を試合参加者に通知、(b) 誤クレームの取消・通報導線、
  (c) クレーム履歴の監査ログ、をセットで設計する。「構造的に排除」とは言わない。
- 撮影者はサークル唯一の稼働メンバーになりやすく、**撮影者の離脱＝サークル全滅**。
  撮影者リテンション（承認負荷の軽減・撮影者特典）をKPIとして持つ。
- データモデルへの布石：PointRecord の player は匿名トラックID（[02](02-architecture.md) に明記）。
  クレーム＝トラックIDとアカウントの紐付けであり、Phase 2で実装可能。

### 第2層：大会インフラ化（閉グラフを越える。Phase 2の主戦略）

サークル内ループはグラフが閉じており飽和する。**新規グラフ同士が接触する唯一の場が草トー大会**：

- **有償パッケージとして設計する**（無償提供にしない）：大会あたり定額（参加費に内包、
  例：32ドロー×数百円）で「希望コートの試合が自動で動画化・ハイライト化」。
  無償だと31試合×処理費＋ストレージがFree予算の外で垂れ流しになる。
- 運用要件を先に確認する：撮影は主催者/参加者のスマホ＋三脚（全コート常時ではなく
  希望コート単位から始める）、会場のアップロード帯域（Wi-Fi待ちキューで夜間送信可）、
  **法務**：イベント単位で数十人の非ユーザー（未成年含む）が映る構造になるため、
  大会モードは専門家レビューのスコープに明示的に含め、参加同意書テンプレートを提供する。
- データモデル：`Tournament`（Match の親）と主催者ロール、コーチ閲覧権限は
  Phase 2 実装時にマイグレーションで追加する（Phase 0〜1 での布石は不要。
  [10](10-phase0-implementation-plan.md) と同判断）。
- **Plan B（K係数不振時の転換先）としての前提検証**：Phase 1 のうちに
  草トー主催者3件のLOI（意向確認）を取る。検証なしに「うまくいかなければ大会へ」
  と言わない（より難しい戦線への転進を撤退先にしない）。

### 第3層：補助チャネル

- テニス系YouTuber・コーチへの無償提供（増幅器）
- SEO：「テニス 動画 編集」等の実用クエリ（記事は薄く、実物デモを厚く）
- **有料広告はK係数とリテンションが立つまで打たない**

### ファネルの仮定値（Phase 0〜1 で実測して置換する）

| 段 | 仮定 | 実測できたら |
|---|---|---|
| アップロード→共有 | 50% | [01](01-mvp-scope.md) の成功指標 |
| 共有→ユニーク視聴 | 3人/共有 | サークルLINEの既読規模から |
| 視聴→登録（導線なし、Phase 1） | 2〜3% | 実測開始点 |
| 視聴→クレームまたは登録（クレーム導線あり、Phase 2〜） | 10% | ここが最大の不確実性 |
| 登録→初回アップロードまたはクレーム完遂 | 40% | Wi-Fi待ちアップロードが障壁（下記） |

- **検算を正面に置く**（アクティブユーザーの月間アップロード1〜2本で計算）：
  - Phase 1（導線なし）：K = 1〜2 × 0.5 × 3 × 0.025 × 0.4 ≒ **0.015〜0.03/月**
  - Phase 2（クレーム導線後）：K = 1〜2 × 0.5 × 3 × 0.10 × 0.4 ≒ **0.06〜0.12/月**
- つまり**このループは単独では成長エンジンにならない（K≪1）**。ループの役割は
  「CAC ほぼゼロの獲得補助＋クレームによるサークル内浸透」であり、成長の主動力は
  大会パッケージ・提携に置く。K目標はフェーズ別に分離する（KPI表参照）。
  Phase 2 でK<0.05が3ヶ月続いたら、ループ改善への追加投資を止め
  大会・B2B2C主導へ全振りする（転換の前提検証は第2層に記載のLOI）。

## オンボーディング（導入体験）

初回体験の敵は「撮影ガイド読了→次の試合まで待つ」の断絶と、**4〜6GBのアップロード障壁**：

1. 登録はLINEログイン＋メール取得（[07](07-advice-delivery.md)）
2. 登録直後に**過去のスマホ動画をそのまま1本アップロードさせる**（Free枠に数えない）。
   画角が悪くても**縮退モードで編集だけは必ず返し**（[03](03-recording-guidelines.md)）、
   「次はこう撮るともっと分かる」を結果として体験させる。ダメ出しだけで終わる初回体験を作らない
3. アップロードは**Wi-Fi待ちキュー＋中断再開**を標準に（モバイル回線で4〜6GBは
   完遂率を潰す第一要因。[10](10-phase0-implementation-plan.md) のアップロードAPI要件）。
   「Wi-Fiに繋がったら自動で送信します」を初回に説明
4. 初回解析完了の通知→編集済み動画→共有ボタンまでを1画面で
5. 撮影ガイドは「次の試合の前」にリマインド配信

## KPI（フェーズ別の焦点。各値に根拠と撤退/転換ラインを持つ）

| フェーズ | KPI | 目標 | 根拠 / 下回った時のアクション |
|---|---|---|---|
| Phase 0 | 初回アップロード完遂率 | 80% | Wi-Fi待ち設計の検証。<60%ならアップロードUX最優先で改修 |
| Phase 0 | 共有率 | 50% | ループの前提。<30%なら共有インセンティブ（ハイライト自動生成の前倒し）を検討 |
| Phase 0 | 区間修正率 | <10% | 編集価値の成立条件。>20%ならCV改善を最優先 |
| Phase 1 | K係数（導線なし） | **0.02以上**（検算上の下限0.015の少し上） | 実測がファネル仮定の検証。0.05を超えたらクレーム導線（Phase 2）の価値仮説が強まる |
| Phase 1 | 週次リテンション（4週） | 40% | 撮影頻度月1〜2の現実線でも配信で戻す設計の検証 |
| Phase 2 | K係数（クレーム導線後） | 0.06以上 | 検算レンジの下限。<0.05×3ヶ月でループ投資を止め大会・B2B2C主導へ（LOI前提検証済みであること） |
| Phase 2 | 撮影者の月次継続率 | >90% | 撮影者離脱＝サークル全滅。承認負荷・特典の設計検証 |
| Phase 2 | Free→Pro転換率 | 3〜5% | フリーミアム一般値**だが本製品での根拠は薄い**。実測1%未満ならFree/Pro境界を再設計。[08](08-operations.md) の成立条件（転換5% or Free原価120円以下）と接続 |
| Phase 2 | LINEブロック率 / 休会率 | <20% / 監視 | 配信の毀損・隠れ解約の可視化（[07](07-advice-delivery.md)） |
| Phase 2 | 月次解約率（休会除く） | <5%、季節月<8% | 年額・休会の効果検証 |
| 共通 | 1試合あたり変動費（実測） | [08](08-operations.md) の表を毎月更新 | 概算との乖離>50%でコストモデル改訂＋価格再検討 |

## フェーズ別の資金・期間計画（持ち出しの見える化）

| フェーズ | 想定期間 | 主な持ち出し | 収益 |
|---|---|---|---|
| Phase 0 | 3〜4ヶ月 | 開発時間＋固定費1万円/月＋Free原価（ユーザー数×約150円/月） | なし |
| Phase 1 | 3〜4ヶ月 | 同上＋GPU変動費増＋**法務一時費10〜30万円**（第三者権利・規約の専門家レビュー。リスク表の必須タスク） | **最小Proを開始**（本数拡張＋スタッツ＋保持延長。アドバイス配信前でも課金開始し、Phase 2を待たない。Freeとの差分は「2本目以降」＋スタッツで作る） |
| Phase 2 | 4〜6ヶ月 | 同上＋Claude API費＋LINEスタンダードプラン移行（約500人到達時、固定費+1万円） | Pro本格化（アドバイス）＋Team＋大会パッケージ |
| Phase 3 | - | コーチ契約費（[06](06-pro-reference-data.md)） | サーブ解析はPro上位機能 |

- 累積持ち出しの概算：Phase 2 開始まで固定費＋Free原価＋法務費で**総額30〜60万円規模**。
- Free原価総額の月次予算：超過が**バイラル成功による**ものなら予算増額＝投資判断
  （Free枠を絞ってループを殺さない。[08](08-operations.md)）。
- **世界展開のstage遷移条件**（[拡張戦略]の表を布石で終わらせない）：
  stage 2（大会・B2B2C）へは Phase 2 開始と同時。stage 3（台湾・タイ）へは
  **国内でPro 1,000人 または 月次経常黒字**を達成し、かつ翻訳・現地チャネル検証の
  ための追加資本（調達 or 自己資金）の判断を行ったとき。条件未達での地理拡張はしない。

## リスクと留意

| リスク | 対応 |
|---|---|
| **第三者（対戦相手・映り込み）の同意なき解析・共有・学習利用** | 規約とガイド明記だけでは不十分（責任のユーザー転嫁）。**実装前に個人情報保護法上の処理根拠を専門家レビュー**（必須タスク）。設計側の先行対応：相手スタッツ非表示既定・削除請求導線・顔ぼかしオプション・学習コーパスからの相手側除外・クレームの本人確認＋撮影者承認（[08](08-operations.md)） |
| 競合の機能追随（SwingVision/AceSenseがアドバイス配信を実装） | 「競合がいない」を前提にしない。12〜24ヶ月の時間限定の先行の間に、規模に依らない非対称資産（大会・コーチ関係、日本環境データ）を確保する（moat参照） |
| LINE依存（BAN・料金改定・ブロック率） | チャネル抽象（[07](07-advice-delivery.md)）、メール必須取得、ブロック率KPI、料金改定はコスト感度分析に含める |
| 季節性・中断（梅雨・冬・怪我） | 年額プラン・休会状態・試合が無い週の復習配信。月別解約カーブを想定してPhase 2で実測比較 |
| 大会・施設の撮影規程 | 撮影ガイドに主催者・相手の許可を明記。共有既定は限定公開 |
| 「解析が外れる」評判リスク | unknown設計＋信頼度表示。マーケ文言でも精度を誇張しない（「全自動」と言わない） |
| 撮影頻度が低く単発利用で離脱 | 練習動画・壁打ちの軽量モード（Phase 1で検討）、休会、復習配信 |
